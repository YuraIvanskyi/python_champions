# code-scenarios: концептуальний огляд можливостей

> **Що це за документ.** Стислий, але повний огляд усіх суттєвих концептуальних можливостей навчального ігрового фреймворку `code-scenarios` — для подальшого ручного використання у магістерській роботі (напрям: викладання інформатики / CS-освіта). Акцент зроблено на *суті можливостей та їхньому навчальному значенні*, а не на деталях реалізації. Технічні подробиці наведено лише там, де вони змінюють педагогічний зміст.
>
> **Примітки для автора** позначено маркером `▸ Нотатка:` — це підказки, як інтерпретувати чи використати матеріал у тексті роботи.

---

## 0. Коротка суть проєкту

`code-scenarios` — це легкий офлайн-фреймворк, у якому учні/студенти пишуть Python-«ботів», що змагаються або кооперуються у покрокових ігрових сценаріях. Рушій безпечно виконує учнівський код, записує відтворювані повтори матчів, аналізує якість коду та надає навчальний зворотний зв'язок. Цільова аудиторія — вчителі, учні середньої/старшої школи, гуртки та секції програмування.

Ключова педагогічна ідея: **навчання програмуванню через ігрове змагання агентів**, де учень пише не «програму заради оцінки», а *стратегію поведінки бота*, яку одразу видно у візуалізації, а якість коду оцінюється окремо від ігрового результату.

▸ Нотатка: це поєднання двох осей оцінювання (ігровий результат + якість коду) — центральна методична новизна, яку варто підкреслити у вступі та висновках.

## 1. Архітектурні принципи (навчальне значення)

Фреймворк свідомо побудований на кількох принципах, кожен з яких має методичний сенс:

- **Простота передусім** — локальний запуск, звичайні файли, JSON/TOML замість бази даних, мінімум залежностей. *Значення:* фреймворк розгортається у шкільному класі без інтернету, серверів чи адміністрування.
- **Детермінованість симуляцій** — один і той самий seed + ті самі боти дають ідентичний результат. *Значення:* справедливе порівняння учнів, відтворюваність для налагодження та демонстрацій.
- **Сильне розділення відповідальностей** — рушій, сценарії, код учня, аналіз і UI не дублюють ігрових правил. *Значення:* демонструє учням і майбутнім розробникам зразок чистої архітектури; спрощує додавання нових сценаріїв.
- **Лише читабельний API для учня** — учень отримує спрощений «вид» стану (`GameView`), а не внутрішні об'єкти рушія. *Значення:* безпека + зниження когнітивного навантаження новачка.
- **ШІ — лише дорадчий** — числові оцінки рахує детермінований аналіз, а мовна модель тільки *пояснює* метрики. *Значення:* уникнення «галюцинацій» в оцінюванні, збереження ролі вчителя.

▸ Нотатка: ці п'ять принципів зручно подати як окремий підрозділ «Методологічні засади» — вони прямо відображають дидактичні вимоги (доступність, справедливість, безпека, поступовість).

## 2. Ядро рушія та модель покрокового ходу

Гра — це **дискретна покрокова симуляція**. На кожному кроці рушій збирає по одній дії від кожного гравця, атомарно застосовує їх через сценарій, фіксує результат ходу і повторює, доки сценарій не завершиться (перемога, поразка або вичерпання ліміту ходів).

Модель ходу розділена так, що одна й та сама логіка обслуговує і «пакетний» безекранний прогон (для вчителя/автоматичного оцінювання), і покрокову інтерактивну візуалізацію в UI. Кожен хід зберігається як запис із номером ходу, дій усіх гравців, поточних рахунків та переліку подій (наприклад, «зібрано ресурс», «атаковано», «промах руху»).

**Основні абстракції:** гравець (`Player` — особистість та ім'я/іконка), бот (`Bot` — гравець + функція прийняття рішення), дія (`Action` — обмежений перелік допустимих команд), результат ходу (`TurnResult`), і контракт сценарію (`ScenarioBase`).

Учнівський код завжди зводиться до однієї відповіді на хід — рядок-команди на кшталт `"MOVE_RIGHT"` чи `"GATHER"`. Це реалізує класичну для ігрового ШІ модель **«відчути → спланувати → діяти»** на кожному ході.

▸ Нотатка: варто наголосити, що обмежений словник дій (enum) — це навчання «типізованим, валідованим інтерфейсам» замість вільних рядків; типова тема з надійності ПЗ.

## 3. Динамічне завантаження учнівського коду

Кожен учень здає **один `.py`-файл**. Рушій завантажує його під час виконання (через `importlib`) і підтримує два стилі:

- **Простий (функційний):** учень пише функцію `make_turn(state)`, що повертає дію.
- **Просунутий (ООП):** учень успадковує клас `BotBase` і реалізує метод `make_turn`.

```python
def make_turn(state):
    if state.on_resource():
        return "GATHER"
    return "MOVE_RIGHT"
```

Перед виконанням код проходить перевірку імпортів (заборонені небезпечні модулі — про це у розділі про пісочницю). Файл також може містити метадані бота — відображуване ім'я та іконку персонажа.

*Навчальне значення:* «один файл = одна робота» повторює природний класний робочий процес; наявність двох API створює **сходинку від процедурного до об'єктно-орієнтованого стилю** — учень «доростає» від функції до класу.

▸ Нотатка: у репозиторії всі приклади написані у функційному стилі; ООП-варіант документований як «наступний рівень». Це можна подати як приклад *масштабованості складності* під різні рівні підготовки.

## 4. Пісочниця (sandbox) та модель безпеки

Учнівський код — недовірений, тож `make_turn` виконується в **окремому дочірньому процесі** з такими захисними шарами:

- **Ізоляція процесом** — окремий інтерпретатор Python; збій бота не роняє основну гру/демонстрацію.
- **Обмеження часу на хід** — жорсткий ліміт стінного часу (за замовчуванням близько 100–200 мс на хід); при перевищенні процес зупиняється, а хід «здається» безпечною дією за замовчуванням (`WAIT`).
- **Заборона небезпечних імпортів** — чорний список модулів (доступ до ОС, мережі, файлів, підпроцесів тощо) перевіряється ще до запуску коду; додатково блокуються небезпечні виклики (`eval`, `exec`, `__import__` тощо) через AST-перевірку.
- **Межа обміну даними** — між рушієм і ботом передаються лише прості дані (JSON): бот ніколи не отримує внутрішніх об'єктів рушія.
- **Безпечна поведінка при помилці** — виняток, зависання чи недопустима дія не зупиняють матч: хід просто втрачається, а турнір/демонстрація триває.

Це **«м'яка ізоляція»**: не контейнер і не seccomp, а прагматичний мінімум, достатній для класу. Розробники свідомо обрали цей рівень як компроміс між безпекою і простотою розгортання.

*Навчальне значення:* учень на практиці бачить, що **нескінченні цикли, помилки й зловживання API мають наслідки** (втрата ходу), але без «падіння» всієї системи. Це також наочна демонстрація ідей «захисту в глибину» та «обмеження можливостей» (capability restriction).

▸ Нотатка: гарний матеріал для окремого підрозділу «Безпечне виконання недовіреного коду» — типовий виклик будь-якої платформи автоперевірки завдань.

## 5. Детермінізм і система повторів (replay)

Уся випадковість — **керована seed'ом**: генерація карти, розміщення ресурсів/перешкод, поведінка вбудованих суперників. Порядок обробки гравців — теж детермінований (сортування за ідентифікатором). Тож однакові вхідні дані завжди дають однаковий матч.

**Повтор (replay)** зберігається у JSON: seed, сценарій, перелік ботів, складність боса (для Boss Fight), покроково — дії та рахунки, а також фінальні результати. Важливо, що зберігаються **дії та події, а не повні знімки стану** — цього достатньо, щоб повністю відтворити матч заново за детермінованими правилами (по суті, це *event sourcing*). У UI повтор можна прокручувати вперед і назад.

*Навчальне значення:* відтворюваність забезпечує **справедливе оцінювання, налагодження й розбір польотів** — учні та вчитель можуть покроково переглянути, чому бот повівся саме так. Це також вводить поняття наукової відтворюваності експерименту.

▸ Нотатка: підкреслити зв'язок «детермінізм → справедливість оцінювання». Для магістерської це вагомий аргумент об'єктивності методики.

## 6. Три ігрові сценарії (сутність і концепції, що їх навчають)

Усі сценарії реалізують один інтерфейс (`setup`, `apply_turn`, `calculate_score`, `is_finished`), але навчають різних тем. Це реалізація патерну «Стратегія/Плагін»: нові навчальні ігри під'єднуються без зміни ядра.

### 6.1 Resource Wars — конкурентний збір ресурсів (вступний рівень)
Сітка 12×12; боти рухаються, збирають ресурси з клітинок, на яких стоять, і змагаються, хто першим досягне порогового рахунку. Немає бою — лише простір і оптимізація. **Концепції:** умовні оператори, цикли, координати, манхеттенська відстань, жадібний пошук, уникнення зіткнень, обізнаність про інших агентів.

### 6.2 Boss Fight — кооперативний PvE проти боса (середній рівень)
Усі учнівські боти **співпрацюють** проти одного боса, керованого рушієм, на меншій карті (10×10). Боти мають здоров'я, можуть атакувати, лікувати себе й союзників. Бос має три рівні складності з різним здоров'ям, уроном і навіть здатністю бити кількох цілей на найвищому рівні. Перемога — здолати боса; поразка — загибель усієї команди. Рахунок розподіляється **пропорційно завданому урону**. **Концепції:** скінченні автомати (атака/лікування/зближення), порогова логіка самозбереження, кооперація кількох агентів, реакція на адаптивного супротивника, допоміжні функції та ролі в команді.

### 6.3 Mana Pools — конкурентний PvP з економікою мани (просунутий рівень)
Велика карта (20×10) з **виснажуваними джерелами мани**. Кожна дія коштує енергії; боти збирають ману поблизу джерел, а суперника можна **штовхнути** (реалізовано як атаку), щоб відтіснити з вигідної позиції. Гра завершується, коли всі джерела вичерпано. **Концепції:** керування ресурсним бюджетом (рух vs атака vs збір), багатокритеріальна оптимізація (місткість джерела vs відстань vs близькість суперника), конкурентна взаємодія та позиційне блокування, робота зі спільним вичерпуваним ресурсом.

▸ Нотатка: три сценарії утворюють природну **дидактичну прогресію** (вступний → середній → просунутий) — це готова структура для розділу «Диференціація складності завдань». Таблиця «сценарій → CS-теми» є у розділі 15.

## 7. Студентський API: читабельний «вид» стану (`GameView`)

Учень взаємодіє зі станом гри **через методи, а не через ключі словника**: `state.my_x()`, `state.score()`, `state.is_walkable(x, y)`, `state.on_resource()`, `state.resource_tiles()` тощо. Для розширених сценаріїв додаються спеціалізовані методи: у Boss Fight — `my_hp()`, `boss_hp()`, `is_boss_adjacent()`, `weakest_ally_id()`; у Mana Pools — `my_energy()`, `nearest_pool()`, `can_gather()`.

Чому саме методи, а не «сирий» словник:
- **Виявність (discoverability)** — автодоповнення в IDE підказує доступні методи; не треба запам'ятовувати структуру даних.
- **Стабільний контракт** — імена методів документовані та незмінні, тоді як внутрішній формат даних може змінюватися.
- **Захист від зміни стану** — API лише для читання; учень не може «зламати» стан гри.
- **Поліморфізм виду** — потрібний різновид `GameView` (звичайний / бос / мана) добирається автоматично.

*Навчальне значення:* це знижує «поріг входу» для новачка й одночасно **демонструє принцип приховування інформації (information hiding)** — учень бачить лише свою перспективу, а не нутрощі рушія.

▸ Нотатка: контраст «методи vs ключі словника» — гарний приклад для тези про *зменшення когнітивного навантаження* в навчальних API.

## 8. Вбудовані суперники (еталонні опоненти)

Для поодинокої практики доступні вбудовані боти двох рівнів: **«жадібний» (Rival)** — діє за прозорою евристикою (йти до найближчого ресурсу/цілі, збирати/атакувати за нагоди), і **«простак» (Rookie)** — частково випадкова поведінка, яка дозволяє новачку виграти. Для кожного сценарію є своя версія опонента (збір ресурсів / бій з босом / збір мани).

*Навчальне значення:* це **сходинки складності**. Жадібний опонент задає зрозумілий еталон стратегії, який учень намагається перевершити; «простак» дає новачку відчуття успіху на старті. Обидва використовують той самий інтерфейс стану, що й учнівські боти, — приклад однорідності архітектури.

## 9. Система аналізу коду (три виміри)

Після матчу код бота аналізується у трьох взаємодоповнюваних вимірах:

- **Статичний аналіз** — за допомогою інструментів Ruff (стиль/лінтинг), Radon (цикломатична складність, індекс супроводжуваності) та власного обходу AST. Вимірюються: складність функцій, глибина вкладеності, довжина функцій, невикористані змінні, заборонені конструкції (небезпечні імпорти, `eval`/`exec`). Окремо оцінюються **евристики «рухового» коду**: чи перевіряє бот прохідність клітинки, чи є цільова логіка, чи передбачено запасний хід.
- **Аналіз під час виконання (runtime)** — телеметрія кожного ходу: час виконання, кількість тайм-аутів, збоїв і недопустимих дій. Це проєкція «спостережуваності» продакшн-систем (затримка, частота помилок) на рівень новачка.
- **Аналіз поведінки (movement)** — повторне програвання повтору, щоб виявити поведінкові антипатерни: «застрягання» на місці, коливання туди-сюди (осциляція), висока частка заблокованих рухів, «застій» рахунку. Це оцінює **алгоритмічну поведінку у світі гри**, а не лише синтаксис коду.

*Навчальне значення:* учень отримує зворотний зв'язок за **кількома незалежними осями якості** — коректність, надійність, читабельність, ефективність і адекватність поведінки. Поведінковий аналіз особливо цінний: він навчає **налагоджувати за спостережуваною поведінкою**, а не лише читаючи код.

▸ Нотатка: тривимірність аналізу (структура коду / виконання / поведінка в грі) — сильна теза для розділу «Автоматизоване формувальне оцінювання». Наголосити, що це виходить за межі звичайного лінтера.

## 10. Навчальний зворотний зв'язок і екран «Code Coach»

На основі метрик генеруються **шаблонні (детерміновані) підказки** — картки зворотного зв'язку з категорією (`runtime` / `logic` / `style` / `efficiency` / `praise`), рівнем важливості (`info` / `warn` / `critical`), заголовком, поясненням, підказкою щодо виправлення та **прив'язкою до конкретних рядків коду** (де це можливо). Якщо проблем немає — бот отримує схвальний відгук. Загалом реалізовано десятки шаблонів на різні ситуації двома мовами.

В UI це подано як **«Code Coach»** — гейміфікований екран у стилі «журналу квестів»: картки-«квести» ліворуч показують проблеми, а панель коду підсвічує відповідні рядки. Клік по картці прокручує код до потрібного місця.

*Навчальне значення:* це **формувальне оцінювання** — миттєві, конкретні, прив'язані до коду поради замість абстрактного «звіту лінтера». Гейміфікація (квести, панелі-пергаменти, персонажі-ментори) знижує емоційний бар'єр для новачка, а прив'язка «підказка → рядок коду» реалізує ефективний патерн «побачив → зрозумів → виправив».

▸ Нотатка: важливо — усі числові оцінки й шаблонні підказки **детерміновані й не залежать від ШІ**. Це аргумент про надійність і прозорість методики оцінювання.

## 11. Система оцінювання (дві осі)

Підсумкова оцінка поєднує **ігровий результат** і **якість коду**:

```
final_score = gameplay_score * 0.7 + code_quality * 0.3
```

- **Ігровий бал** нормується у шкалі 0–100 відносно порога сценарію (напр., у Resource Wars 15 ресурсів = 100 балів) — це робить різні сценарії порівнюваними.
- **Бал якості коду** починається зі 100 і зменшується за штрафами (порушення стилю, висока складність, глибока вкладеність, задовгі функції, заборонені конструкції, невикористані змінні, низька супроводжуваність). Синтаксична помилка обнуляє бал.
- Ваги (0.7 / 0.3) та поріг **налаштовуються для кожного сценарію** окремим конфігом.
- Окреме правило: якщо бот падав під час виконання або перевищував тайм-аут на хід, максимум балу за якість коду **обмежується згори** — «код, який не працює надійно, має обмежену якість, хоч би як гарно виглядав».
- Ваги з `scenario.toml` **валідуються** (сума gameplay + code = 1.0); пороги нормалізації беруться з того ж файлу, включно з користувацькими перевизначеннями у збірці exe.

*Навчальне значення:* методика прямо доносить думку, що **інженерія ПЗ оцінює і продукт, і процес**: працює розв'язок (70%), але важлива й підтримувана, безпечна, читабельна реалізація (30%). Це формує правильні пріоритети з самого початку.

▸ Нотатка: формула 70/30 і «обмеження за збій» — конкретні, некриті («не чорна скринька») правила оцінювання; це варто протиставити «непрозорим» автогрейдерам.

## 12. Дорадчі ШІ-звіти (опційно)

Опційно система може згенерувати **людиночитабельний звіт** через локальну мовну модель (OpenAI-сумісний ендпойнт, напр. через Ollama/vLLM; передбачено кілька невеликих моделей). Модель отримує **вже готові метрики й шаблонні підказки** та формулює короткий підсумок для учня і нотатки для вчителя **мовою інтерфейсу** (українська або англійська).

Жорсткі запобіжники:
- **ШІ не змінює числові оцінки** — лише пояснює вже пораховані метрики.
- **ШІ не пише повних розв'язків** і не переписує учнівський код (дозволені хіба короткі приклади на 1–2 рядки).
- Якщо ШІ вимкнено — **нуль мережевих звертань**; якщо модель недоступна — система коректно відкочується до шаблонних підказок.
- Звіт явно маркується як «дорадчий».

*Навчальне значення:* це модель **пояснюваного дорадчого тьюторства**, узгоджена з принципом «автопідказки не замінюють роль вчителя та рубрику оцінювання». Локальні моделі зберігають офлайн-придатність для класу.

▸ Нотатка: підкреслити етичний/методичний аспект — ШІ навмисно позбавлено «влади» над оцінкою; це відповідь на ризик «галюцинацій» і на дискусію про роль ШІ в освіті.

## 13. UI/UX: настільний застосунок у стилі RPG

Графічний інтерфейс — один настільний застосунок на Pygame CE з набором екранів: **меню-лаунчер** (вибір сценарію, режими «Практика» та «Клас», вибір бота(ів), опонента, складності боса, карти й seed), **симуляція** (покроковий матч із кнопками крок/пуск/пауза), **результати** (рейтинг, метрики та **експорт оцінок CSV** для вчителя), **повтор** (перегляд і прокрутка збережених матчів), **Code Coach** (аналіз коду з вкладками учнів у класному матчі), **посібник для написання бота** (вбудована документація) та **налаштування** (мова, звук, увімкнення ШІ, модель ШІ, параметри карти).

Візуальний стиль — середньовічне фентезі: панелі-пергаменти/камінь/дерево, персонажі-іконки для ботів, фонова музика під настрій екрана. Плитки й елементи навмисно **великі й контрастні — розраховані на демонстрацію через проєктор** у класі. Кожен бот отримує ім'я та іконку-персонажа, тож анонімні `.py`-файли стають «героями».

*Навчальне значення:* режими **«Практика» (учень + ШІ-опонент)** і **«Клас» (2–N учнівських ботів)** відповідають індивідуальній та змагальній формам навчання. Ігрова візуалізація створює **часовий зв'язок «рішення в коді → наслідок на екрані»**, а ідентичність ботів підтримує впізнаваність і «турнірну культуру» в класі. Потік «меню → симуляція → результати → коуч/повтор» повторює педагогічний цикл «зіграв → осмислив → покращив».

▸ Нотатка: гейміфікація й «персоналізація» ботів — важливий мотиваційний чинник; варто згадати як фактор залученості (engagement).

## 14. Двомовність (локалізація)

Увесь інтерфейс, шаблони зворотного зв'язку, підказки ШІ, назви сценаріїв, посібники та підписи локалізовано **двома мовами — українською та англійською** (з відкатом на англійську). Навіть шрифт основного тексту перемикається залежно від мови (латиниця/кирилиця). Не перекладаються лише сам код учня та числові оцінки.

*Навчальне значення:* повна українська локалізація уможливлює **розгортання в українськомовному класі** без окремої збірки — важливий чинник доступності та рівності в CS-освіті.

▸ Нотатка: для української магістерської це прямий плюс — фреймворк «рідною мовою» для учнів, які ще не володіють англійською термінологією.

## 15. CLI та пакування (для вчителя й розгортання)

Крім GUI, є **консольний інтерфейс** для вчителя/автоматизації: запуск матчу (`run`), окремий аналіз коду (`analyze`), генерація ШІ-звіту (`report`) і запуск GUI (`gui`). Підтримуються прапорці для вибору сценарію, одного або кількох ботів, цілої теки з ботами, seed, опонента, складності боса та вимкнення аналізу для швидкої ітерації.

Проєкт **пакується у самодостатній застосунок для Windows** (через PyInstaller) — без потреби встановлювати Python на учнівських машинах; інструменти аналізу (Ruff/Radon) вкладено в збірку. Результати матчів зберігаються в **теку користувача** (`%LOCALAPPDATA%\CodeScenarios\results`), а не поруч із exe; при першому запуску конфігурації копіюються з bundle. Вчитель може **експортувати CSV** з оцінками сесії з екрана результатів; вихідний код бота **знімається в snapshot** у теку сесії для Code Coach.

*Навчальне значення:* **подвійний режим** (GUI для учня, CLI для пакетного/автоматичного прогону вчителем) і офлайн-збірка різко знижують поріг розгортання в школі. Прапорець `--seed` забезпечує відтворювані демонстрації та чесне порівняння.

## 17. Головні тези для висновків

1. **Дві незалежні осі оцінювання** (ігровий результат + якість коду) роблять методику одночасно мотивувальною та інженерно коректною.
2. **Детермінований, прозорий рушій оцінювання** (без «чорних скриньок» і без впливу ШІ на бали) забезпечує об'єктивність і відтворюваність.
3. **Поступове зростання складності** — від простого `make_turn` до ООП, від збору ресурсів до конкурентної стратегії — реалізує диференційоване навчання.
4. **Багатовимірний зворотний зв'язок** (структура коду, виконання, поведінка в грі) виходить за межі звичайного лінтера й навчає налагоджувати за спостережуваною поведінкою.
5. **Офлайн, україномовність і гейміфікація** прямо адресовані реальному шкільному класу як середовищу впровадження.

▸ Нотатка: якщо потрібні точні числа (розміри карт, пороги, коефіцієнти штрафів, повний перелік методів API, кількість шаблонів зворотного зв'язку тощо) — скажи, і я додам окремий технічний додаток із конкретикою та посиланнями на файли.
